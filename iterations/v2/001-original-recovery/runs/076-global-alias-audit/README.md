# Run076 — original-VA global alias audit

Original: `Porsche.exe`, SHA-256 `ddd748fdbe6d2030e31f9257a4e01852749460b6b58560a6b4a8559d3799ff39`. The scanner inventories file-scope C++ definitions under `source/recovered` and `source/platform` whose symbol names end in an eight-digit VA; it skips probe TUs. It is a candidate finder, not proof that a C++ variable physically represents that original cell. Findings and limits are in `aliases.json`.

The first three collision groups are confirmed multiple native owning definitions for one original address: `0x005deb1c` has two DWORDs; `0x005deb74` and `0x005deb78` each have four owners. Original x86 references show `0x005deb1c` written by heap-copy, display-clock and renderer state paths. `0x005deb74/78` are written as paired source-pointer/line DWORDs, while current recovered modules keep independent diagnostic pairs. These require shared storage and a focused consumer trace before changing owners.

`0x005e8e50` is another duplicate C++ owner (`char[32]` heap label and `char[1]` null fallback). PE section mapping puts it in `.data` virtual zero-fill: `.data` raw bytes end at VA `0x005e7000`; this VA is beyond the raw extent but within the section's virtual extent. Ghidra's `defined-data.jsonl` also records the byte as zero. Original ASM reads a byte at `004b7327`/`004b74c0`, and the indexed references show no explicit write to the address. This supports a zero-byte fallback use, not the recovered 32-byte heap-label claim; trace the readers and producer/call paths before assigning the original object's full extent or semantic type.

Known shared views are separated from duplicate storage: `0x006573e8` and renderer dimensions `0x00657a48/4c` point into the single `ApplicationStateArena`; `0x006a57d8` has one `thread_start_lock` owner and `window_paint_lock` is a reference alias in `source/platform/window_links.cpp`. Original startup stores a nullable translation-table address `0x005df934` at `0x0069e5a0`; the DWORD width is correct but `window_channels_initialized` is semantically misleading. `0x006b77a0` is an original configuration object; the suffixed `window_configuration_address` is a host pointer to its native storage, not a second original cell.

Reproduce candidate discovery with `py -3 scripts/research/audit-v2-global-aliases.py`. The inventory covers production translation units, not header declarations, dynamically generated symbols or link-time storage; no source was changed by this audit. Next traces are recorded per finding, and no native game behavior or runtime acceptance is claimed.
