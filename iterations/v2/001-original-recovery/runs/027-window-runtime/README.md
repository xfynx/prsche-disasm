# Run027 — window path and timed callback consumer

Source: immutable `local/game/Porsche.exe`, SHA256 `ddd748fdbe6d2030e31f9257a4e01852749460b6b58560a6b4a8559d3799ff39`. Index query: `CreateWindowExA|RegisterClassA|PeekMessageA` in `research/binary-index/static/imports.jsonl`, then `005b22c0|005b2310` in Porsche.exe `references.jsonl`, and caller/callee checks in `calls.jsonl` and `disassembly.asm`. The import IAT uses PE FirstThunk, as documented in `research/binary-index/README.md`.

The first relevant Win32 window class registration is `0x53ac20:0x53ace0` (`RegisterClassA`, IAT `0x5b2310`). The sole indexed direct `CreateWindowExA` consumer is `0x53bb00:0x53bc4c` (IAT `0x5b22c0`), called by `0x53b8d0:0x53b8da`; the call uses the class name global `0x69e5a8`, module handle `0x6b7794`, style global `0x5dea88`, and a configuration object at `0x6b77a0`. The original `0x53b8d0` then stores the resulting HWND in `0x6b7bf8` and enters the message loop. The apparent startup `0x536e50` is DirectInput initialization (`GetModuleHandleA` and `DirectInputCreateA` at `0x536e95/0x536e9c`, COM calls thereafter). It is not window initialization. This is evidence for the next bounded consumer, not a claim that the first game window has been rebuilt.

`0x5366e0..0x536763` is a 16-slot timed callback consumer, not a Win32 message pump. It compares last/current ticks (`0x69de24`, `0x6b7c40`), reads slots at `0x69dd20..0x69de1f`, marks a due callback active around invocation, ORs callback results, and advances its next tick using the current global tick after callback return. `0x5367b0..0x5367b2` always returns zero. Both have full instruction-backed C++ bodies in `window_runtime.cpp`; callback behavior remains a typed recording boundary.

The complete direct `0x53bb00..0x53bcaa` CreateWindowExA consumer is also recovered. The fixture records ordered `GetSystemMetrics`, `AdjustWindowRectEx`, `CreateWindowExA`, cursor and `0x5739b0` calls, then compares configuration positions, state and return value. The original x86 and native C++ matched on 35 scheduler and 64 window cases: fullscreen/windowed, stored/default position, style flag, override, channel initialization and CreateWindowExA failure/success. Run `py -3 scripts/research/verify-v2-window-runtime.py`; `verification.json` records source/probe hashes. Win32 calls are controlled boundaries; an actual visible HWND and message procedure are outside this comparison.

The complete `0x536e50` DirectInput consumer, `0x53ac20` class registration and `0x53b8d0` message loop are still unrecovered. Next step: trace `0x53ac20` callers/indirect vtable references and recover its full state/callee sequence, then compare registration → CreateWindowExA → HWND/message state with original x86. The registered window procedure at `0x53aba0` must be independently traced; registration alone does not establish its behavior.
